# Design: harden-tool-edges

## Context

Three command-path edges are implemented and tested but unspecified:
compile's duplicate-stem guard (src/commands/corpus.rs:630-686), verify's
shared artifact routing (src/verify.rs:339-375, :438, :615), and audit's
merged-row disambiguation (src/audit.rs:425-476, :818). Each reuses an
existing decision: compile's guard mirrors the command scope law's
labeled-refusal discipline, verify routes through the same
`citation_corpus::artifact_dir` the compile and model-check stages use,
and audit folds through the one merge seam its pack and vacuity rows
already use. The remaining work is to state that behavior in the three
capability specs and carry it into the dual-format layers.

## Goals / Non-Goals

- Goals: specify the implemented edge behavior scenario-by-scenario;
  keep each capability's delta self-contained (plain openspec delta plus
  full `layer.md` sidecar); leave every existing requirement, exit code,
  and artifact byte untouched.
- Non-Goals: changing implementation, adding commands or flags, changing
  exit codes, or claiming behavior richer than the cited code and tests
  demonstrate. No new evaluator, no new routing scheme, no new suffix
  scheme.

## Decisions

- **Decision: compile's stem collision is an invocation refusal BEFORE
  lint, with its own label.** The harm is artifact collision, not
  identity: a lint-clean same-stem corpus also shares an intent id
  (lint's `id_matches_file` pins an ordinary file's id to its stem), so
  an identity refusal would only catch the lint-clean subset and would
  name the wrong problem; a pre-lint collision would slip through. The
  guard therefore runs first, names `duplicate_artifact_stem` and both
  paths, and exits 2 with the out-dir never created.
  - Alternatives considered: a warning plus last-write-wins (rejected —
    it is the silent overwrite this guard exists to remove); a lint
    finding (rejected — lint-clean only, and it would describe a
    filename accident rather than the artifact harm); post-compile
    detection (rejected — the earlier file's artifacts are already
    clobbered).
- **Decision: "same file twice" is decided by canonical path identity.**
  One path collected twice (repeated argument, overlapping roots) yields
  the same bytes and the same artifacts, so it is one input. Identity is
  the canonicalized path the guard already records; comparing stems
  would refuse a legitimate repeated argument, and hashing contents
  would read every file for no additional discrimination.
  - Alternatives considered: content hashing (rejected — cost without a
    difference the path does not already prove); counting occurrences
    (rejected — turns a harmless repeat into a refusal).
- **Decision: the refusal keeps the corpus notes.** Corpus construction
  can skip a file (ingestion cap, non-ingestable input) and attaches a
  labeled note; the refusal must re-attach those notes exactly as the
  adjacent empty-corpus refusal does, or an early refusal hides why part
  of the corpus was skipped.
  - Alternative considered: drop notes on refusal (rejected — an
    envelope that refuses while hiding an input problem reports less
    than the run knows).
- **Decision: verify resolves every location through one routing
  decision, never a private re-derivation.** The properties source, the
  check report, the modules the scope digest hashes, and therefore the
  digest's per-file hashes are all the same file's artifacts; resolving
  them independently is the `stale_artifact` class the shared decision
  exists to remove. One call to `routed_artifact_dir` per spec feeds all
  three joins, so duplicate stems are read per file and corpus-unique
  stems keep the flat layout.
  - Alternatives considered: verify refuses duplicate stems (rejected —
    compile and orchestrate already accept and route such corpora, so
    verification evidence would vanish for corpora the pipeline builds);
    copying or linking flat artifacts (rejected — duplicate bytes and an
    ambiguous winner on the next write); leaving the model gate routed
    and the props gate flat (rejected — exactly the split-brain the
    single decision prevents).
- **Decision: audit renames the FOLDED row, never the oracle row.** The
  prior-report diff matches rows by `scenario_id`; oracle ids are the
  recorded evidence's own ids, so renaming them would orphan prior
  evidence. The folded `bind:`/`pack:` row is generated by the run, so
  it yields the id and takes the first free `~<n>` suffix (`~2`, `~3`,
  …). Both rows survive with their own classes, so advisory classes and
  the exit contract are untouched.
  - Alternatives considered: a labeled refusal (rejected — an oracle id
    that happens to spell a generated key is a naming accident, not a
    reason to fail an audit); dropping one row (rejected — that is the
    silent loss the uniqueness rule prevents); hashing the suffix
    (rejected — opaque and not the first-free determinism the corpus
    order already gives).
- **Decision: determinism is part of the requirement, not an
  implementation detail.** First-free suffix assignment over a sorted,
  corpus-derived row set means no counters, random state, or map
  iteration order; repeated assembly yields identical keys and
  byte-identical serialization.
- **Decision: ADDED, not MODIFIED.** No deployed requirement changes
  text; each new behavior is an orthogonal edge with its own scenarios.
  The layer sidecars are full snapshots (the deployed tables plus the new
  rows) so the archive companion can deploy them verbatim after re-keying
  `cap.layer` to `cap`.

## Risks / Trade-offs

- Risk: the specs drift from the code they describe → each requirement
  names the label, paths, and observable envelope fields the cited tests
  assert; the layer rows derive properties whose predicates restate those
  assertions.
- Risk: "byte-identical" is read as covering duplicate-stem corpora too →
  the verify requirement scopes byte-identity to corpus-unique stems and
  names the routed layout separately.
- Risk: a `~<n>` key reads as a new scenario id → the audit requirement
  states the oracle row keeps its id verbatim and the renamed row keeps
  its class, so only the generated row's key changes.
- Risk: the full-snapshot sidecars go stale if another change touches the
  same layers first → re-snapshot the three layers immediately before
  archive, then run the sidecar lint.
- Trade-off: a refusal on duplicate stems makes a previously "successful"
  last-write-wins invocation exit 2. That is the intended hardening, and
  it is the behavior already shipped; the spec records it rather than
  introducing it.

## Migration Plan

None. The behavior is already in the binary; this change adds
requirements and layer rows only. Archive deploys the sidecars; nothing
is removed and no caller changes.

## Open Questions

- Whether a suffixed advisory row should match a same-suffixed row in a
  prior report is deferred: the current diff keys by the final merged id,
  and advisory classes never affect the exit code, so the question can
  wait for a diff-observability change.
- Whether compile should expose the colliding stem in the machine-readable
  envelope as a structured field (rather than only in the message) is
  deferred; the requirement pins the observable message, paths, hint, and
  exit code the tests assert.
